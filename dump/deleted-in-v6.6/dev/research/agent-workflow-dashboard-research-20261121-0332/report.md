# Local Multi-Agent Workflow Board — UI Research

## Summary

**Verdict (index-based, high confidence on patterns, not on pixel-perfect screenshots):** No researched product matches the target exactly. The target is *not* a true DAG product — its 14 phases (`intake → charter → plan → [human plan approval] → implementation → pre-test review → [human adjudication] → fix → unit tests → manual test campaign / waived → [human final review] → done → [delivery approval] → delivered`) are essentially **linear, with 4 human gates, one fix loop, and one waived branch**. The best-fitting composite is therefore:

- **Overview + gates inbox:** LangChain Agent Inbox + Linear Inbox/Triage + PagerDuty “Mine” list
- **Per-task graph:** GitLab stage-columns / GitHub Actions job graph, simplified to a horizontal stepper — *not* Airflow/Dagster/Temporal free-form DAG rendering
- **Trace:** Temporal History (Timeline / Compact / All) + LangSmith trace tree, collapsed by default like Linear issue history
- **Detail layout:** Linear / GitHub PR — main column (goal, docs, activity) + right properties sidebar (status, prerequisites, blockers)
- **Human action forms:** LangGraph HITL decisions (`approve / edit / reject / respond`) + GitHub PR review (batch pending comments, then Submit with one verdict; merge-box prerequisites checklist) + Prefect paused-flow typed input form
- **Anti-flood:** Linear Priority inbox, snooze, badges and mark-all-read; PagerDuty acknowledge-stops-escalation. Replace the tmux notification stream with *counts and queues, refreshed on page load*.

All 12 ranked ideas in §6 are implementable as bash-generated static HTML + a tiny Python `http.server`-style POST handler that writes only into pre-defined markdown slots. Nothing in the shortlist needs a database, WebSockets, a JS framework, or a graph-layout library. The expensive parts of the source products — live streaming, time-travel/forking, pan/zoom DAG layout, full-text search, real-time presence — are explicitly listed as **do not copy**.

Sources are official docs/product pages wherever possible, read 2026-11-21 via the web index (`index` flag throughout; no product UI was logged into in a live browser, so descriptions are doc-verified, not screenshot-verified live).

## Findings

### 1. AI agent orchestration UIs

#### 1.1 LangGraph Studio / LangSmith Studio + LangSmith tracing

- **(a) Overview for many runs:** Studio itself is *per-graph, per-thread*, not a fleet dashboard — you pick a graph/deployment, then pick a thread from a dropdown/list in the right pane. The fleet view lives in LangSmith tracing (project → list of traces/runs, filterable). Lesson: Studio is the wrong model for the overview; LangSmith's trace list is the right one.
- **(b) Detail view:** “Studio is a specialized agent IDE that enables visualization, interaction, and debugging” with two modes: **Graph mode** “exposes the full feature-set … including the nodes traversed, intermediate states” and a simpler **Chat mode** for chat agents. Thread history populates the right-hand pane; a **granularity slider** shows more/less detail, individual turns/nodes/state keys collapse/expand, and you can switch **Pretty vs JSON**. Source: https://docs.langchain.com/langsmith/studio and https://docs.langchain.com/langsmith/use-studio (`index`). LangSmith traces add the second density: a trace is nested runs (model call, tool, retrieval); **Details** = execution tree with inputs/outputs per run, **Trajectory** = simpler ordered message/tool sequence. That two-density idea was described in secondary coverage of the official observability docs; treat the exact view names as `index`, single-source.
- **(c) Waiting on human:** Via LangGraph interrupts / breakpoints in Studio (see §3.1), not via Studio's graph itself. Studio can set an **Interrupt** breakpoint and inspect/edit state at the pause.
- **(d) Anti-flood:** Collapse/expand + granularity slider + Pretty/JSON toggle — i.e. *progressive disclosure of state*, not notifications. No push stream in the detail view concept.
- **(e) Steal / Don't copy:** *Steal:* (1) the granularity slider → in the local board, a simple “Summary / Full” toggle for the trace (two generated pages or `<details>` blocks, no JS needed); (2) graph-on-left, thread-history-on-right layout for task detail. *Don't copy:* time-travel, “Edit node state → Fork”, playground prompt editing, datasets/experiments — all need a runnable graph server + checkpointer DB.

#### 1.2 LangGraph human-in-the-loop + Agent Inbox

- **(a) Overview:** Agent Inbox is a dedicated queue of *interrupted threads only*: a table with thread identifier, timestamp of interruption, context (proposed content), and status; graphs appear in a sidebar and interrupted threads are auto-fetched. Source (example repo docs, secondary): https://deepwiki.com/langchain-ai/agent-inbox-langgraph-example/4-agent-inbox-integration (`index`).
- **(b) Detail:** Clicking a thread opens a detail view with the interrupt's markdown **description**, the action request and its arguments, plus toggles to view thread **state / description** in a side panel.
- **(c) Waiting on human — the single closest pattern to the target:** Official HITL docs define exactly four decision types per interrupt, configured per tool/action: **`approve`** “Execute the tool with the original arguments”, **`edit`** “Modify the tool arguments before execution”, **`reject`** “Skip executing this tool call entirely and return rejection feedback”, **`respond`** “Return the human's message directly as a synthetic tool result, for ‘ask user’ style tools”. Source: https://docs.langchain.com/oss/python/langchain/human-in-the-loop (`index`). The frontend docs generalise it: the UI “renders a review card with approve/reject/edit options”, the card can live “inline in the transcript, in a review queue, in an admin dashboard, or in a modal”, and `allowedDecisions` controls *which buttons are shown per action*. Source: https://docs.langchain.com/oss/python/langchain/frontend/human-in-the-loop (`index`). Agent Inbox names the same set Accept / Edit / Respond / Ignore.
- **(d) Anti-flood:** Only *interrupted* threads enter the inbox — running/completed work does not notify. Stale interrupts are suppressed (only shown if attached to the last message with nothing after it, per Agent Chat UI implementation notes via DeepWiki).
- **(e) Steal / Don't copy:** *Steal:* (1) **A gates-only inbox page** — nothing else may appear there; (2) **per-gate allowed-decisions** — plan approval gets Approve/Request-changes, a Q&A slot gets only Respond (a textarea), a finding gets FIX/DROP/DEFER (the local analogue of reject/edit/respond); don't show irrelevant buttons. *Don't copy:* the LangGraph server, checkpointer persistence and `Command(resume=…)` machinery — the local board's “resume” is simply *the watcher/agent noticing the markdown slot is now filled*.

#### 1.3 AutoGen Studio (Microsoft)

- **(a) Overview:** Not a run fleet view. Main surfaces are **Team Builder**, **Playground**, and **Gallery** (reusable teams/agents/models/tools). Source: http://microsoft.github.io/autogen/0.4.7/user-guide/autogenstudio-user-guide/usage.html (`index`).
- **(b) Detail:** Team Builder canvas = “a main team node and a set of connected agent nodes”, built by drag-and-drop from a component library *or* by toggling visual mode off and editing the JSON directly. Playground shows the run as a conversation-like stream: review artifacts (images, code, text), monitor the team's **“inner monologue”**, view **performance metrics (turn count, token usage)**, track tool usage / code execution results.
- **(c) Waiting on human:** Human input is conversational (a human agent / user-proxy in the team, chat in Playground), not a structured gate/queue. No approval inbox.
- **(d) Anti-flood:** Weakest here — the inner-monologue stream *is* a flood surface, mitigated only by separating it into the Playground run view rather than a global feed.
- **(e) Steal / Don't copy:** *Steal:* (1) **Visual ⇄ text toggle** — every rendered doc/graph on the local board should have a “view source (markdown)” twin, exactly AutoGen's visual-builder ⇄ JSON toggle; (2) a small metrics strip per task (turns/tokens in AutoGen → in the local board: elapsed time in phase, # findings, # Q&A open, retry count — all parseable from the worklog). *Don't copy:* drag-and-drop team builder, live chat playground — needs a runtime + WebSockets.

#### 1.4 CrewAI — Flows, `plot()`, and AMP Traces

- **(a) Overview:** CrewAI AMP (cloud) project dashboard → **Traces tab** listing crew/flow executions. Open-source CrewAI itself has no local fleet UI; visualisation is per-flow.
- **(b) Detail:** AMP trace view is explicitly sectioned: **1. Execution Summary** (total/prompt/completion tokens, # requests, execution time, estimated cost), **2. Tasks & Agents**, **3. Final Output**, **4. Execution Timeline** (“when each task started and ended, helping you identify bottlenecks or parallel execution”), **5. Detailed Task View** on click (task key/ID, status completed/running/failed, agent, output). Source: https://docs-platform.crewai.com/platform/en/features/traces (`index`). Built-in tracing docs list the same contents: agent decisions, task execution timeline, tool usage, LLM calls, performance metrics, error tracking. Source: https://docs.crewai.com/v1.15.21/en/observability/tracing (`index`). Separately, `flow.plot()` / `crewai flow plot` “will generate an HTML file” with “nodes representing the tasks in your flow, with directed edges indicating the flow of execution” — a *single generated HTML file you open in a browser*. Source: https://docs.crewai.com/v1.15.10/en/concepts/flows (`index`).
- **(c) Waiting on human:** No structured approval queue in the OSS UI; human input is a task/flow step, not an inbox item.
- **(d) Anti-flood:** Trace *batching* on the producer side, and summary-first trace layout (metrics header, drill down only on click).
- **(e) Steal / Don't copy:** *Steal:* (1) **`plot()` as architecture proof** — a credible flow graph can be one generated HTML file with inline SVG, no app server; this validates the target's bash-generated approach; (2) the 5-section trace page order (summary strip → steps/agents → final output/deliverable → timeline → per-step detail) maps 1:1 onto task detail (header metrics → phase stepper → deliverable → worklog timeline → per-phase docs). *Don't copy:* AMP cloud account, token/cost telemetry pipeline.

#### 1.5 Temporal Web UI

- **(a) Overview:** “The main Workflows page displays a table of all Workflow Executions within the retention period”, listable/filterable by Status, Workflow ID, Workflow Type, start/end time and custom search attributes; **Saved Views** store frequent filter queries for one-click reuse (stored in the browser). Plus a pre-built **Task Failures view** — still-running workflows with ≥5 consecutive task failures are auto-flagged, and the flag clears on recovery: a *threshold, not a per-failure alert*. Source: https://docs.temporal.io/web-ui (`index`, opened and read in full).
- **(b) Detail:** Header metadata (start/close/duration, Run ID, type, task queue, parent, state transitions), Input/Results, then **History with four views of the same data: Timeline** (chronological summary, click an event for full detail), **All, Compact** (“a logical grouping of Activities, Signals and Timers”), **JSON**. Also **Relationships** (parent/child tree), **Pending Activities** tab, Workers, Call stack, Metadata. Source: https://docs.temporal.io/web-ui (`index`). The Timeline visualisation groups related events (Scheduled+Started+Completed → one Activity row spanning its duration), colour = outcome (green Completed, red Failed), a retry icon + attempt number, points for single events (markers/signals), zoom/filter by event type. Source: https://temporal.io/blog/lets-visualize-a-workflow (`index`).
- **(c) Waiting on human:** No approval inbox, but two transferable bits: pending work is a **tab with a count** (in the tutorial, “The Pending Activities tab … is labeled with a 1, which indicates that there is currently one failing Activity”), and humans act from the UI via Signal/Update/Cancel/Reset/Terminate dialogs with a single JSON input. Sources: https://docs.temporal.io/web-ui (`index`).
- **(d) Anti-flood:** Compact grouping (3 raw events → 1 logical row), event-type filtering, Saved Views, and the 5-failure flagging threshold.
- **(e) Steal / Don't copy:** *Steal:* (1) **Four densities, one dataset** — for the worklog: Timeline (one line per worklog entry) / Compact (grouped by phase) / All (raw markdown) — generatable as three anchors on one page; (2) **count-badged “Pending” tab** on task detail and on the overview (“3 gates waiting”); (3) user-metadata summaries rendered *on* the timeline bar — Temporal shows an activity's `Summary` text directly on its timeline label and in purple next to history events so you needn't expand. Source: https://docs.temporal.io/develop/go/platform/enriching-ui (`index`). *Don't copy:* event-history replay/reset, visibility query language, workers/call-stack — all server/DB-backed.

#### 1.6 OpenAI Agents SDK tracing

- **(a) Overview:** Logs → Agents: a list of **sessions**, filterable by model/status/date (“Use Add filter to filter by model, status, or date”); session summary shows status, model, start, last activity, # turns, token usage. Source: https://developers.openai.com/api/docs/guides/agents-api/tracing (`index`).
- **(b) Detail:** Session → timeline + list of **turns** → expand a turn → **steps/spans** grouped under the root agent or subagent that performed them. Clicking a span opens a details panel: for Agent spans — type (root/subagent), ID/name/model/instructions, usage, duration, outcome; Generation — recorded input/output; Tool — tool name, arguments, result. “The timeline shows the order of the steps and which ones overlap” and “Each span shows its duration and outcome status.” Sources: https://developers.openai.com/api/docs/guides/agents-api/tracing and https://openai.github.io/openai-agents-python/tracing/ (`index`). Span taxonomy is fixed: agent / generation / function / guardrail / handoff (+ task/turn wrappers).
- **(c) Waiting on human:** None — tracing is read-only observability.
- **(d) Anti-flood:** Hierarchy does the work: you see turns, not tokens; spans nest under their agent so sub-agent chatter is collapsed under its parent by default.
- **(e) Steal / Don't copy:** *Steal:* (1) **Fixed event-type taxonomy with distinct icons/colours** for the worklog (phase-start, agent-report, gate-opened, human-decision, test-result, message) — the local equivalent of span types; (2) **nest sub-agent reports under the phase/agent that spawned them** (HTML `<details>`), never as top-level timeline items. *Don't copy:* span storage/export pipeline, token-level capture.

### 2. Workflow / DAG UIs

#### 2.1 Apache Airflow

- **(a) Overview:** DAGs list: per DAG, schedule/next run, latest run status, a **bar chart of recent runs**, and at a glance “exactly how many tasks succeeded, failed, or are currently running”; tag filtering and a **pause toggle per DAG** in the list. Airflow 3 adds a home view with DAG/task-instance history counts and success/failure rates over a selectable range. Sources: https://airflow.apache.org/docs/apache-airflow/2.8.4/ui.html and http://apache-airflow-docs.s3-website.eu-central-1.amazonaws.com/docs/apache-airflow/stable/ui.html (`index`).
- **(b) Detail:** Tabs for the *same* run data: **Grid** — “A bar chart and grid representation of the DAG that spans across time. The top row is a chart of DAG Runs by duration, and below, task instances” (rows = tasks, columns = runs, each cell a colour-coded status box; click a duration bar or a status box and a **details panel updates in place**); **Graph** — nodes = tasks, edges = dependencies, coloured by the selected run's state; **Gantt** (duration/overlap, bottlenecks); **Calendar** (day cells coloured by outcome); **Code** (the source that generated the DAG). Task-instance actions from the panel include Clear (re-run), Mark success, Mark failed.
- **(c) Waiting on human:** No approval concept; the human acts by marking/clearing task instances.
- **(d) Anti-flood:** The grid *replaces* time-series noise with pattern recognition — a column of red is visible without any alert; auto-refresh is in-place, not a notification stream.
- **(e) Steal / Don't copy:** *Steal:* (1) **Grid transposed for the local board:** rows = tasks, columns = the 14 phases, each cell a coloured status square — the whole fleet's progress as one pattern-recognisable matrix on the overview (pure HTML table); (2) click-a-cell → details panel pattern → in static HTML, cell links to `task.html#phase` anchors; (3) per-row **pause toggle** analogue: a “muted / parked” flag file per task that removes it from the gates inbox and dims its row. *Don't copy:* Gantt/duration analytics, calendar-over-months, log streaming — need a metrics DB.

#### 2.2 Prefect

- **(a) Overview:** Flow Runs dashboard: **Filters at the top** (date interval, run state, flow name, deployment, tags), a **run-history area** (recent runs by time and duration), then rows each showing flow/run name, tags, **state, scheduled/actual start, elapsed time, and number of completed task runs**. Source: https://prefect-284-docs.netlify.app/ui/flow-runs/ (`index`).
- **(b) Detail:** Run page: state, elapsed, IDs, version, run count, infrastructure, tags, Logs, Task runs, Subflow runs, and a graph view. Prefect's history is instructive: the original **Radar** (concentric dependency view) was criticised by users as hard to read and was **retired in favour of a timeline/flow-run graph** that shows execution over time and can expand/collapse subflows (Prefect release notes via community archive, `index`, secondary). Current docs still describe Radar on the v2 page — *sources disagree by version; the direction of travel (radar → timeline) is the reliable claim.*
- **(c) Waiting on human — second-closest gate pattern:** Interactive workflows: a flow can **pause or suspend until it receives input in the UI**; `pause_flow_run(wait_for_input=…)` takes a typed model (built-in type, Pydantic `BaseModel`, or `RunInput`), Prefect “uses the fields and type hints … to validate” the input, you can attach a **dynamic Markdown description that appears in the UI when the flow pauses**, set defaults with `with_initial_data`, and “the flow run pauses until a user clicks the Resume button in the Prefect UI, enters a name, and submits the form”. Source: https://www.prefect.io/docs/v3/advanced/interactive (`index`).
- **(d) Anti-flood:** State/tag/date filtering as the primary navigation; scheduled vs ad-hoc runs in one list distinguished by state chips.
- **(e) Steal / Don't copy:** *Steal:* (1) **Typed gate forms generated from a schema** — locally: the Q&A file's question type determines the widget (free text → textarea, choice → radios), the gate's markdown context is rendered *above* the form (Prefect's markdown description), defaults pre-filled; (2) completed-count on the overview row (“7/14 phases”, Prefect's completed-task count). *Don't copy:* Radar, suspend-to-object-storage, automations/Slack alerts.

#### 2.3 Dagster

- **(a) Overview:** Top nav: Overview, Assets, Jobs, Runs, Schedules/sensors. **Runs page lists all runs filterable by job, run ID, status, tag**; Asset catalog filterable by key/group/kind/tags, with a **Global asset lineage** graph across everything. Source: https://github.com/ssup2/dagster/blob/HEAD/docs/docs/guides/operate/webserver.md (`index` — official docs source in the Dagster repo).
- **(b) Detail:** Job page Overview tab = graph of ops. **Run details: stats header (ID, status, date, duration) at top; upper-left a Gantt chart of how long each step took; bottom pane = filterable events/logs**, with a toggle between **structured event logs** (enriched, categorised, labelled by asset/step) and **raw compute logs** (stdout/stderr). On failure the page adds an **Errored section** listing problem steps next to the timeline, timeline bars turn red, and logs expose the full message/stacktrace on click; Re-execute (all or subset) sits top-right. Sources: webserver doc above; https://dagster-university.vercel.app/dagster-essentials/lesson-3/4-viewing-run-details (`index`).
- **(c) Waiting on human:** No approval queue; human action = launch/re-execute runs from the graph.
- **(d) Anti-flood:** Structured-vs-raw log separation + log filtering by step/level — you default to the curated event stream, raw logs are opt-in.
- **(e) Steal / Don't copy:** *Steal:* (1) **Structured timeline by default, raw worklog behind a toggle/tab** — same lesson as Temporal/OpenAI, independently confirmed; (2) an explicit **“Blocked / Errored” callout box** at the top of task detail when a gate is open or a step failed, instead of burying it in the timeline. *Don't copy:* asset lineage across projects, partitions/backfills, GraphQL launchpad.

#### 2.4 GitHub Actions

- **(a) Overview:** Actions tab → workflows in a left sidebar → list of runs per workflow. No cross-repo fleet view.
- **(b) Detail:** “Every workflow run generates a real-time graph that illustrates the run progress… The graph displays each job in the workflow. **An icon to the left of the job name indicates the status of the job. Lines between jobs indicate dependencies.** To view a job's log, click the job.” Steps are *not* graph nodes — they live inside the job's log page. Source: https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph (`index`).
- **(c) Waiting on human:** Environment approvals exist in the product but are not covered in the cited graph docs — *could not verify from the pages read; do not rely on specifics.*
- **(d) Anti-flood:** Graph + status icons replace log-watching; run list is paginated history, not a stream.
- **(e) Steal / Don't copy:** *Steal:* (1) **Status as an icon *before* the name, everywhere** (list, graph, timeline) with a fixed legend — success ✓ green, failed ✕ red, running spinner/yellow, queued dot, **skipped grey** (the exact visual needed for “manual test waived”); (2) two-level detail discipline: phases are nodes, *within-phase* steps are log content, never nodes. *Don't copy:* live real-time graph updates (needs push), matrix-job expansion.

#### 2.5 GitLab CI

- **(a) Overview:** Pipelines index per project; crucially a **pipeline mini graph** is embedded wherever a pipeline is referenced (index page, commit page, merge-request page): stages as collapsible groups, net result per stage at a glance, hover/click to expand jobs. Sources (docs mirrors): https://docs.devnetexperttraining.com/static-docs/GitLab-CI-CD/pipelines/ and https://gitlab.ipsemg.mg.gov.br/help/ci/pipelines.md (`index`).
- **(b) Detail:** Full pipeline graph on the pipeline page: jobs grouped **by stage (same stage = same column)** or **by `needs` dependencies** — a grouping toggle. Failure reason is visible by **hovering the failed job in the graph** and on the job page, not only in logs. Manual jobs can be run by clicking the **play button directly in the graph**.
- **(c) Waiting on human:** Manual jobs *are* the gate: the pipeline visibly waits at that job until a human clicks play in the graph itself.
- **(d) Anti-flood:** Mini-graph as ambient status in MR/commit context — no separate notification needed to know pipeline state.
- **(e) Steal / Don't copy:** *Steal:* (1) **Stage columns, not free DAG layout** — for a linear workflow this is the cheapest correct graph: 14 columns (or wrapped rows), jobs/artefacts stacked inside, CSS only, no layout engine; (2) **mini-graph everywhere** — a compact 14-dot/14-segment strip on every overview row, inbox item and doc header; (3) gate action *in* the graph (the phase node for a gate contains its Approve link/form anchor). *Don't copy:* downstream/multi-project pipelines, DAG `needs` optimisation.

#### 2.6 Argo Workflows

- **(a) Overview:** Workflow list with phase Pending/Running/Succeeded/Failed, start/completion/duration (described in secondary Skyhook docs: https://docs.skyhook.io/application/jobs/argo-workflows, `index`).
- **(b) Detail:** DAG defined by task `dependencies` (diamond A → B,C parallel → D is the canonical docs example: https://argo-workflows.readthedocs.io/en/latest/walk-through/dag/, `index`); UI detail shows total/completed/**current**/failed node counts, step progress with dependencies and per-step time, per-step logs, DAG view + timeline + artifact browser (secondary source above).
- **(c) Waiting on human:** Engine has a `suspend` template (pause until resumed) — conceptually a gate node in the DAG itself.
- **(d) Anti-flood:** Phase counts summary header rather than per-pod events.
- **(e) Steal / Don't copy:** *Steal:* the **counts header** (“14 phases: 9 done · 1 running · 1 waiting-human · 3 pending”) as the task-detail subheader and per-row on the overview. *Don't copy:* almost everything else — Kubernetes pods-per-step, artifact store, workflow archive DB are the opposite of file-based local.

### 3. Human-in-the-loop / approval inbox UIs

#### 3.1 LangSmith Agent Inbox / LangGraph HITL
Covered in §1.2 — the reference design for the gates inbox: interrupted-only queue, per-item allowed decisions (approve/edit/reject/respond), markdown description as the review context, state inspectable beside the action form.

#### 3.2 GitHub pull request review

- **(a) Overview:** PR list rows summarise review state in words (“Review required / Approved / Changes requested”) and checks state in icons; `review-requested:@me` search is the personal review queue.
- **(b) Detail:** Conversation **timeline** interleaves comments, reviews, commits and status events; sidebar holds linked issues/discussions, projects/milestones, reviewers with per-reviewer state icons (✓ approved, changes-requested, comment, dot = still waiting). Sources: https://docs.github.com/en/pull-requests/concepts/giving-reviews (`index`).
- **(c) Waiting on human — reference design for adjudication:** Reviewer works file-by-file in **Files changed**, can **mark each file Viewed to collapse it**, with a **progress bar in the header showing how much of the PR you've covered**; line comments stay **pending (only visible to you, editable) until you submit the review in one batch** with a summary comment and exactly one verdict: **Comment / Approve / Request changes**. Source: https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request (`index`). Below the timeline, the **merge box** lists *prerequisites still unmet* (review required, changes requested, checks failing/pending) and only enables Merge when all pass (merge-box specifics from search-result summaries, `index`, secondary — verify in product if quoting externally).
- **(d) Anti-flood:** Pending-review batching (no notification per comment), Viewed-collapse + progress, stale-approval dismissal on new push (an approval visibly *expires* when the thing it approved changes).
- **(e) Steal / Don't copy:** *Steal:* (1) **Adjudication = pending batch + single submit:** tick FIX/DROP/DEFER per finding (radios in one form), add notes, one Submit writes the whole review file section — never one form per finding; (2) **merge-box → “Delivery prerequisites” checklist** on task detail: plan approved ✓, all findings adjudicated ✓, unit tests pass ✓, manual test done-or-waived ✓, final review approved ☐ — with the Deliver/Approve button (form) disabled-looking/explained until all pass; (3) **Viewed checkbox per rendered doc** stored as a tiny marker in the review file, collapsing already-read docs; (4) stale-gate rule: if implementation changes after plan approval, the approval badge shows “stale”. *Don't copy:* line-level diff comments, suggested-change apply, CODEOWNERS routing.

#### 3.3 Linear Inbox + Triage

- **(a/c) Inbox:** “The Inbox is your notification center… You’ll receive an Inbox notification for key events on your subscribed issues” (auto-subscribed when you create, are assigned, or are mentioned). A **Priority tab “separates notifications that need your attention from other updates” and is selected by default**; you can configure what counts as Priority, the **badge count**, and grouping. Actions without opening: mark read/unread (`U`), **mark all read** (`Option/Alt U`), delete, **snooze (`H`)** — “Snoozing hides a notification from your Inbox until the selected time. When that time arrives, the notification reappears.” Quick search filters by title/ID/type/assignee/team/project/priority. Cap: 2,000 open notifications retained. Source: https://linear.app/docs/inbox (`index`, opened and read in full).
- **(a/c) Triage:** “Triage is a special inbox for your team… review, update, and prioritize issues before they are added to your team's workflow.” Exactly four exits, each one keystroke: **accept `1`** (optional comment, → default status), **decline `2`** (→ Canceled, optional explanation comment), **mark as duplicate `3`/`MM`** (attachments/requests move to the canonical issue), **snooze `H`** (hidden until chosen time *or new activity, whichever comes first*). To ask for more info: comment and *keep it in Triage or snooze it*. Source: https://linear.app/docs/triage?_rsc=1pb9v (`index`, opened and read in full).
- **(d) Anti-flood — the most complete model researched:** subscription-scoped notifications (only work you're involved in), Priority-vs-All split, snooze-until-activity, mark-all-read, delete-all-read, badge = count of *actionable* items only, and (in the issue feed) **collapsing similar consecutive history events and older activity between comments** to reduce clutter. Sources: Inbox/Triage docs above; collapsed history: http://Linear.app/changelog/2025-04-03-collapsed-issue-history (`index`).
- **(e) Steal / Don't copy:** *Steal:* (1) **Two inboxes, not one:** *Gates* (= Triage: items that block an agent, each with a small fixed verb set) vs *FYI* (= Inbox: agent reports/completions, mark-read/snooze only) — never mix them in one stream; (2) snooze/DEFER that **resurfaces on new activity** (locally: a deferred gate reappears highlighted when the worklog gets a newer entry for that task); (3) keyboard-first queue processing (`j/k` + `1/2/3`) — cheap vanilla JS or even plain numbered links. *Don't copy:* Triage Intelligence/Rules automation, rotations/PagerDuty integration (paid, server-side AI/routing).

#### 3.4 Humanloop

- **(b/c) Review queue:** Human evaluations: SMEs judge generated Logs in the **Review tab**; “Turn on **Focus mode** and start providing judgments” — one item at a time, full context; “When the last judgment is provided, the Run is marked as complete.” Feedback can also be applied **directly in the rating column of the table, or from the drawer** (row click opens a right-hand drawer with full log detail); finish with **Mark as complete** (top-right); aggregate results in the **Stats tab**. Judgments come from a configurable schema (e.g. 5-point scale by default, or multi-select options each with positive/negative valence, plus instructions text shown to the reviewer). Sources: https://humanloop.com/docs/guides/evals/run-human-evaluation and https://humanloop.com/docs/v4/guides/evaluation/evaluating-with-human-feedback (`index`).
- **(d) Anti-flood:** Focus mode + progress-to-complete replaces a long undifferentiated list.
- **(e) Steal / Don't copy:** *Steal:* (1) **Focus mode for the gates inbox:** “Gate 2 of 5 — [task] Plan approval” with the full charter/plan rendered, verdict form, and Next — plus a progress bar; (2) **judgment schema = instructions + fixed options rendered above the form** (for findings: severity, file/line, reviewer rationale from the review file, then FIX/DROP/DEFER radios). *Don't copy:* evaluator management, dataset/version comparison, stats analytics.

#### 3.5 PagerDuty

- **(a) Overview:** Incidents page defaults to **Triggered + Acknowledged** only; tabs/filters **Assigned to me / My teams / All**, status chips (removable), sort by Urgency; columns: #, Status, Priority, Urgency, Type, Title, Created, # Alerts, Service, Assigned to. **Bulk action bar** appears on checkbox selection: Acknowledge, Resolve, Reassign (+ add a note and change status in the same step). **Recent Activity tab** is a separate, quieter feed (Service, Title, Time, Activity). Sources: https://docs.pagerduty.com/incident-management/incidents/navigate-incidents-page (`index`).
- **(b) Detail:** Each incident has a **Timeline tab** “showing timestamps of each incident status along with all other actions taken and notifications sent”, **filterable by event/action type**. Source: https://docs.pagerduty.com/incident-management/incidents/overview (`index`).
- **(c/d) The acknowledge pattern:** States are only **Triggered → Acknowledged → Resolved**. “An acknowledged incident … claims ownership … and **halts the escalation process**. While an incident is acknowledged, notifications are not sent until the acknowledgement timeout is reached” — then it re-triggers. By default notifications fire on trigger only, not on ack/resolve. Colour counts on the dashboard: triggered = red, acknowledged = orange, none = blue.
- **(e) Steal / Don't copy:** *Steal:* (1) **“Seen / working on it” as an explicit state for a gate** — locally an `ACK` marker the human can set (one click writing a line in the Q&A/review file) that *stops the watcher re-announcing that gate* and shows the gate orange/“acknowledged” instead of red/“waiting”; with a simple rule that new agent activity on that task un-acks it; (2) red/orange/blue count header on the overview (waiting / acknowledged / clear). *Don't copy:* escalation policies, on-call rotations, push notifications.

### 4. Issue / task tracker detail views

#### 4.1 Linear issue detail

- **(b) Layout (from official docs + changelog, `index`):** Three depths — **peek** (Space, preview without leaving the list), side panel, **full view**. Full view: main column = breadcrumb (team > parent), title + description (inline-editable), **sub-issues list with progress**, then the **activity feed**; right **properties sidebar** = status, priority, assignee, labels, project/milestone, cycle, estimate, due date, parent, plus a **Relations section (Blocked by / Blocks / Related)**. Activity feed **interleaves history events (status, assignment, label changes) with comments** in one chronological stream; similar consecutive events are grouped/collapsed. Sub-issues: created from the parent with `+ Add sub-issues`, inherit team/priority/project, parent can auto-close when all sub-issues are done. Sources: https://linear.app/docs/parent-and-sub-issues?_rsc=1e0jx, https://linear.app/docs/my-issues, http://Linear.app/changelog/2025-04-03-collapsed-issue-history (`index`; the three-depth layout detail is partly from a secondary research file synthesising Linear docs — flagged accordingly in notes).
- **(a) Overview complement — My Issues:** a curated personal view (Assigned / Created / Subscribed / Activity tabs) where assigned issues are **grouped in focus order: urgent, SLA-bound, blockers, cycle work, other active, triage, backlog, completed**, started-before-unstarted within each group. Source: https://linear.app/docs/my-issues (`index`).
- **(e) Steal:** (1) **Main column + properties sidebar** as *the* task-detail template: main = goal, acceptance criteria, rendered docs, trace; sidebar = phase, agent, claim state, blocked-by/blocks (from the claim ledger / inbox), delivery prerequisites; (2) **peek** — overview rows expand inline (`<details>`) to show goal + current gate without a page load; (3) focus-order grouping on the overview: **Waiting-on-you first, then blocked, then running, then done** — not alphabetical/chronological.

#### 4.2 Jira issue view

- **(b) Layout:** Two forms — issue detail view *within* a board (selected issue + detail pane) and the full view: header with project/key/summary and **issue actions including the workflow transitions menu** (the current status and its allowed next transitions are buttons in the header, not a separate admin screen), **Activity tabs** below, share/export, and side **Development** and **Agile** panels. The **History tab records field changes** (creator, field edits, attachments, comment/worklog/link deletions) while the **Activity tab has the same information plus comments**. Source: https://confluence.atlassian.com/jirasoftwareserver0912/working-with-issues-1346049816.html (`index`).
- **(e) Steal:** (1) **Transition buttons in the header** — the task's *next legal human actions* (Approve plan, Waive manual test, Approve delivery) rendered as buttons at the top of task detail, driven by current phase; illegal actions simply absent; (2) split trace tabs: **History (state changes only) vs Activity (state changes + messages/comments)** — two filters over the same worklog file. *Don't copy:* configurable workflows, JQL, permissions — configuration surface is the disease, not the cure, for a local board.

#### 4.3 GitHub issue / PR timeline

- Covered for PRs in §3.2. For issues, the transferable pattern is the same single chronological timeline where *system events are one-line, low-emphasis rows* (labelled, assigned, milestoned, closed/reopened, review requested/given) and *human/agent content is full-width blocks* — visual weight ∝ decision value. The PR sidebar's per-reviewer state icons and the Conversation timeline are the cited official behaviours (https://docs.github.com/en/pull-requests/concepts/giving-reviews, `index`).

|---|---|---|---|---|---|
| LangSmith Studio | Per-graph thread list (weak fleet view) | Graph nodes traversed + state per node | Thread history, granularity slider, Pretty/JSON | Breakpoints/interrupts (via LangGraph) | Collapse + granularity control |

| Jira | Board columns | Workflow diagram (admin) | **History vs Activity tabs** | **Transition buttons in issue header** | Tab separation |

**Three convergent lessons (each confirmed by ≥3 independent products):**
1. **Summary first, raw last.** Temporal Compact, Dagster structured logs, OpenAI span nesting, Linear collapsed history, CrewAI summary header all default to a curated, grouped view and hide the raw stream behind a toggle.
2. **The gate is a queue item with a tiny verb set, not a message.** Agent Inbox (4 verbs), Linear Triage (4 exits), GitHub review (3 verdicts), PagerDuty (Ack/Resolve) — every successful HITL UI restricts the human to 2–4 named decisions per item, with free text as an *attachment* to a decision.
3. **Counts, not streams, for ambient awareness.** Temporal pending-count tab, Linear badge config, PagerDuty red/orange counts, Airflow succeeded/failed/running counts, Argo node counts — the overview communicates by numbers and colour blocks; the stream exists only inside a detail view.

### 6. Ranked shortlist — 12 most adoptable ideas for the file-based local board

Cost key (bash-generated HTML + tiny localhost Python server, markdown files as only storage): **Trivial** = HTML/CSS emitted by the generator, no server change · **Low** = one form POST → server writes into a pre-defined markdown slot/line · **Medium** = new parser convention in the markdown files + generator logic, still no JS framework/DB.

| # | Idea (source) | Maps to target board | Implementation sketch | Cost |
|---|---|---|---|---|
| 1 | **Gates-only inbox, separate from an FYI feed** (Agent Inbox; Linear Triage vs Inbox) | **Gates inbox** + overview header | Generator scans all tasks for open gates (unfilled Q&A slots, unadjudicated findings, pending approvals) → `inbox.html` listing *only* those, each linking to its form anchor. Everything else (completions, reports) goes to a separate Activity page nobody must clear. | Trivial (read-only generation) |
| 2 | **Horizontal stepper with gate-shaped nodes** (GitLab stage columns; GitHub Actions icons; LangGraph nodes) | **Task detail graph** | 14 phases as a flex row of boxes joined by arrows (pure CSS). States: done ✓ green, current ● pulsing/outline, waiting-human ⏸ amber with person icon, failed ✕ red, **waived ⊘ grey**, future ○ muted. Gate phases drawn as diamonds/amber cards, distinct from work phases. Fix loop shown as a small ↩ annotation under review→fix, not a drawn cycle. | Trivial |
| 3 | **Mini-stepper on every row** (GitLab mini graph) | **Overview** | Each task row/card embeds a 14-segment strip (coloured cells, tooltip = phase name) + “7/14” count (Prefect completed-count). Whole fleet's shape visible without opening anything. | Trivial |
| 4 | **Delivery-prerequisites checklist / merge box** (GitHub PR merge box) | **Task detail** (sidebar) + gates inbox | Sidebar checklist parsed from files: plan approved, findings adjudicated (n/n), unit tests pass, manual test done *or waived*, final review approved. Each item ✓/✕/⏳ with a link to the exact form/doc that satisfies it. Delivery-approval form sits directly under it and its help text names the first unmet prerequisite. | Low (read-only checklist; approval itself is #8's form) |
| 5 | **Per-gate allowed verbs only** (LangGraph `allowedDecisions`; Agent Inbox config) | **Answer / adjudication forms** | Form type is driven by gate type: plan/final/delivery approval → Approve / Request-changes (+ comment); Q&A → Respond only (textarea per question); finding → FIX / DROP / DEFER radios. Never render a generic comment box as the primary action. | Low |
| 6 | **Batch adjudication: pending edits + one Submit** (GitHub pending review; Humanloop Mark-as-complete) | **Adjudication form** | All findings for a task in *one* `<form>`: a radio group per finding + one notes field, single Submit → server writes all verdict slots in the review file atomically. Same pattern for Q&A: all open questions for a task in one form, one Submit fills all answer slots in the Q&A file. | Low |
| 7 | **Collapsed, grouped, filterable trace** (Temporal Timeline/Compact/All; Linear collapsed history; Dagster structured-vs-raw) | **Trace timeline** | Worklog rendered three ways via anchors/tabs: *Compact* (default — one row per phase transition + human decision + test result; consecutive agent progress entries collapsed into “×N updates” `<details>`), *All* (every worklog line), *Raw* (the markdown source). Filter chips = pure-CSS/anchor subsets (Human decisions only / Tests only). System events as one-line muted rows; human decisions and agent deliverables as full blocks (GitHub timeline emphasis rule). | Trivial–Medium (grouping rule = same-phase consecutive entries) |
| 8 | **Main column + properties sidebar layout, with peek** (Linear/Jira/GitHub PR detail) | **Task detail** (whole page) + overview | Detail: left/main = goal, acceptance criteria, test direction, stepper, rendered docs, trace. Right sidebar (sticky CSS) = phase, owner agent, claim/ledger state, Blocked-by/Blocks (from claim ledger + inbox files), prerequisites (#4), timestamps/time-in-phase. Overview rows get a `<details>` peek expanding goal + open gate inline. | Trivial |
| 9 | **Focus mode queue processing + progress** (Humanloop Focus; Linear Triage keys; GitHub Viewed progress bar) | **Gates inbox** | Inbox items ordered (oldest gate first / blocked-tasks first per Linear My Issues focus order); header “Gate 2 of 5”; after a submit, server redirects to the next open gate (or an “Inbox zero 🎉” page). Optional: `j/k` + `1/2/3` via ~30 lines of vanilla JS — progressive enhancement only. | Low (redirect-after-POST); JS optional |
| 10 | **Acknowledge + snooze/defer that resurface on new activity** (PagerDuty Ack; Linear snooze) | **Gates inbox** + overview | One-click ACK writes a marker line (gate id + timestamp) — gate turns amber “acknowledged”, watcher/board stops counting it as urgent. DEFER writes a defer-until note. Either state auto-clears when the task's worklog mtime/entry count advances past the marker (generator compares timestamps). Overview header shows PagerDuty-style counts: 🔴 waiting · 🟠 acknowledged · 🔵 clear. | Low–Medium (one marker file/section + timestamp comparison) |
| 11 | **Typed answer forms with rendered context above** (Prefect paused-flow form + Markdown description; Humanloop schema instructions) | **Answer forms** + doc viewer | Above each form, render the full context doc (charter for plan approval, review file excerpt per finding, question + any agent-provided options for Q&A). Widget by convention in the markdown: a question followed by `options:` → radios; otherwise textarea; pre-fill defaults already present in the slot. Server validates non-empty and writes *only* inside the slot markers — the file stays diff-readable. | Low–Medium (slot-marker convention is the work) |
| 12 | **Fleet matrix + counts header as the overview's top** (Airflow Grid + counts; Argo counts; Temporal Saved Views) | **Overview** | Top: count tiles (tasks by phase, gates waiting, failed tests, delivered this week). Below: matrix table — rows = tasks, columns = 14 phases, cells = coloured status squares linking to `task.html#phase` (Airflow grid transposed). Filter = a few pre-generated views (All / Waiting on me / Running / Blocked / Done) as separate generated pages or anchor-filtered sections — Temporal Saved Views without a query engine. | Trivial |

**Explicitly NOT in the shortlist (needs backend/DB/framework):** live/push updates and WebSocket streams (AutoGen Playground, Actions live graph); pan/zoom DAG layout libraries (Prefect Radar — which Prefect itself retired — Dagster lineage, Argo DAG view); time-travel/fork/edit-state (LangGraph Studio); re-execute-from-here (Dagster/Airflow Clear); full-text/log search infrastructure; token/cost telemetry (CrewAI/OpenAI); diff line-comments and suggestion-apply (GitHub); AI triage/routing and rotations (Linear/PagerDuty paid tiers). A meta-refresh (`<meta http-equiv="refresh">`) or manual reload after each generator run is an adequate substitute for live updates at single-human scale.
