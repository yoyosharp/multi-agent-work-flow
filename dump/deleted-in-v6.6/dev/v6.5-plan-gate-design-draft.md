## 1. The problem, in the user's words (2026-11-24)

- When Claude Code uses Superpowers to generate a plan, the hook blocks
  writing it to Superpowers' own folder. Accepted — the agent wrote it
  into the task folder instead, and that is the working shape.
- Those plans carry `Dn..` decisions linked to `Sn..` steps. The user
  doesn't know where they come from or what they mean (fine if they have
  meaning for the agent).
- Reviewing a plan is hard to track: what / where / why / how for each
  decision, and no detailed A-slot like `review.md` / `qa.md`.
- Asking the plane for a summary doesn't scale across multiple tasks —
  the plane CLI is hard to track too.
- Direction: a detailed plan is now required, so make it the same shape
  as the other gate files. Watching and preparing is fine, but the final
  verdict on editing the file stays with the user.

## 2. Where Dn / Sn come from (verified in the package tree)

- Not from the workflow at all. The package has no plan template and
  never defines D or S.
- They come from the Superpowers `writing-plans` skill the worker uses:
  the plan writer numbers its **Decisions D1, D2…** and its **Steps
  S1, S2…**; a link like "D2 → S4" means "this decision governs that
  step." Keep the notation — it has meaning for the agent.

## 4. Proposed shape (assistant proposals — NOT decided)

### 4.1 `plan.md` — the fourth gate file

- New `plan.template.md` → per-task `plan.md` (canonical location;
  settles the Superpowers-folder tension — the narrative plan stays
  linked as detail, not replaced).
- Status table at top: D# | Decision | Steps | Status
  (OPEN / ADJUDICATED-held / RELEASED / APPROVED / DROPPED).
- One block per decision, written by the plan author:
  `### Dn — <title>`; **What** · **Where** (files + the S-steps it
  governs) · **Why** (reason / charter item it traces to) · **How**
  (approach chosen); **Verdict A-slot** (user fills:
  APPROVE / REVISE / DROP — vocabulary not yet confirmed, see §5);
  **Ack** (worker appends after applying).
- Plan-review P-findings cite the Dn they target, so a finding lands on
  a decision instead of floating in the worklog.
- Gate rule: impl starts when every decision is APPROVED or DROPPED.
  REVISE sends just that decision back into the plan loop; the rest
  stays approved.
- Release semantics identical to qa/review: the user's fill is held and
  editable; it releases at the next REPL touch on the task, or by a
  board Submit (fill+release in one step).
- Board: plan decisions become a third S3 gate form alongside Qn/Fn,
  and open decisions show in the gates inbox.

### 4.2 The key map (draft inventory, drawn from the package tree)

| Key | Lives in | Minted by | Meaning |
|---|---|---|---|
| **Qn** | `qa.md` | worker | Question needing a human answer; A-slot = the answer |
| **Fn** | `review.md` | §3.1 pre-test reviewer | Finding in implemented code; A-slot = FIX / DROP / DEFER |
| **Dn** | `plan.md` (v6.5, proposed) | plan author | Plan decision — what / where / why / how; A-slot = APPROVE / REVISE / DROP |
| **Pn** | `worklog.md` plan-review entry | plan-review subagent | Finding about the plan; plan-loop feedback, never a review.md entry |
| **Tn** | `worklog.md` test-result-review entry | test-result-review subagent | Finding about test evidence (unit / manual phase) |
| **Sn** | narrative plan doc (Superpowers) | plan author | Implementation step; D-rows cite the S-steps they govern |
| **B1–B6** | `anchors.md` | — | Evidence anchors checked at every CLOSE |
| **A-slot** | `qa.md` / `review.md` / `plan.md` | — | Not a numbered key — the human's fill inside a Q/F/D row |
| **kind:** | worklog plane lines, inbox | plane | Message category: question / decision / blocker / status / handoff; WAITING kinds: answer / dependency / access / plan-approval |

- Letters don't collide (Q/F/D/P/T/S/B are distinct). P and T findings
  live only in worklog entries — the two keys with no file of their own,
  which is why they get lost.
- Proposed home: `docs/workflow/keys.md`, linked from `anchors.md`, the
  gate templates, and the skills that mint keys. Freeze rule: no key
  exists unless it is on this table.
- Task-local key process (per §3.6–3.7): introduce freely inside one
  task; plane flags it to the user at the next REPL touch as an
  IMPORTANT item; at task finish the plane suggests promote or retire
  (promote if used more than once in the task or names a concern another
  task could share; retire if single-use and task-specific); the helper
  decides from that suggestion and records it. Promoted keys get a row
  in `keys.md` (noted as promoted from that task); retired ones stay
  task-local and the decision is recorded in the task worklog.
- Same rule for `kind:` values — a new `kind:` value goes through the
  same task-local → promote-or-retire process.
- Retire, never reuse: a dead key stays on the map marked RETIRED with
  the reason, so old files stay readable; its letter is never
  reassigned. One letter, one meaning, forever.
- Collision rule at promotion: the helper checks the letter against the
  map first — if the letter is already taken with a different meaning,
  the key stays task-local and the helper notes why, rather than
  renaming anything mid-flight.
- Scope note: today the helper's allowlist is `_bin/` scripts,
  `0.scratch/`, memory files, and `*.local.json` — `docs/workflow/keys.md`
  is NOT in it, and the hook would deny the write. The v6.5 build would
  add an exact-file carve-out for `keys.md` in the helper branch. That
  makes the helper the *only* role that can write the map: the plane is
  confined to `.history/`, the worker to its worktree and task dir, the
  scoper to `_pending/`. So "helper scope only" becomes literally true.

### 4.3 Mutual agreement + the small gate (revised after the user's correction)

- **Trigger, same discipline as §3.1:** the worker's plan-complete
  declare (`state: WAITING kind:plan-approval` + plan pointer) triggers
  the plane to spawn plan-review itself within one poll cycle — no
  human order, no waiting for the next REPL touch.
- **Agreement = both sides holding for the same rev:**
  - Plane side: `plan-review … VERDICT: CLEAN (rev N)` in the worklog.
  - Worker side: the worker's explicit acceptance of that same rev —
    a worklog line like `plan rev N accepted — <what I will implement,
    in one line>`, written *after* the CLEAN, not before. A bare "ok"
    doesn't count; it has to cite the rev and state the commitment.
  - If either side is missing, or the rev moved, the gate is closed
    and nothing gets surfaced.
- **Worker voice inside the loop:** when plan-review says
  CHANGES-NEEDED, the worker answers each P-finding by **revise** (new
  rev, loop re-runs) or **contest** (`contest Pk — <reason + evidence>`).
  A contested finding goes back to the plane, which either upholds it
  (worker must revise) or drops it, recorded in the worklog. The drop
  stays visible in the trace when the plan reaches the user.
- **The small gate: revision-stamped agreement.** The plan carries a
  revision marker (`Plan rev: N`, bumped on every revision); the
  plan-review entry cites the rev it checked. The plane may not surface
  a plan — no gates-inbox entry, no "plan ready" message, no board plan
  gate — unless the worklog holds a CLEAN *and* a worker acceptance for
  the *current* rev. A post-CLEAN revision re-closes the gate. The board
  shows "plan in review" vs "plan ready for your verdict" distinctly.
- **Negotiation limit (decided: 3 passes).** A round is one review
  verdict on one plan revision. Three CHANGES-NEEDED cycles without
  mutual agreement, and the loop stops — no fourth pass on the agents'
  own initiative. What surfaces: the current rev, the still-open
  P-findings with both sides' positions side by side (reviewer's demand
  vs. worker's contest and reason), and the D-rows for the user's
  verdict — as a distinct `plan negotiation limit reached` item in the
  gates inbox, reading as "needs your ruling" rather than "ready for
  review." The count resets when the user rules: a verdict sending a
  decision back for revision gives the new rev a fresh loop — the limit
  caps *agent-only* rounds between the user's touches, not the total
  work on the plan. (Decided 2026-11-24: 3 passes.)

### 4.4 Worker display labels (in v6.5 scope, confirmed 2026-11-24 — build NOT ordered yet)

- User's correction: the task-ID idea (old §4.4, now §6) was NOT what
  he meant. Agents already resolve task aliases (slugs) well enough —
  the problem is only on the human's side: when the plane says
  something like "worker-002", he cannot tell which worker is meant.
- Verified in the package tree: there is NO `worker-001/002` numbering
  anywhere. The `Worker` column in `workers.md` is a free-form
  "identity label" the worker writes at DECLARE (parallel-agents.md),
  and nothing specifies what goes there — so in practice it is
  arbitrary (`w`, empty) and the plane/board fall back to claim-row
  numbers (`claim #N`), which are meaningless to the human. That is
  the actual defect: no worker naming rule, and human-facing messages
  use row numbers instead of a label.
- Proposed shape (assistant):
  - **Default label = task short** (slug minus the `YYYY-MM-DD-`
    prefix — the "short" the board already derives). With 1 worker per
    task, worker ≡ task, so the short identifies the worker with zero
    extra typing.
  - **Optional override param on `/worker`:** `/worker <slug> [label]`
    — the user sets a custom display label at launch when the short
    isn't clear enough (similar shorts, or a nickname he prefers).
    The label flows command arg → worker boot → `Worker` column at
    DECLARE. The param is the override, not the mechanism: making it
    the only mechanism would force him to type a label for every
    launch.
  - **Plane rule:** in every human-facing message (status sweep, wake
    lines, gates inbox, board claim lines) the plane names a worker by
    its `Worker`-column label, never by claim-row number. Row numbers
    stay as the internal index only. (status.sh already parses the
    Worker column; board.sh prints `claim #N` today and would print
    the label instead.)
  - **Collision rule:** labels must be unique among live workers.
    Default labels collide only if two live tasks share the same short
    (same descriptive tail on different dates — possible). On
    collision the plane falls back to the full slug for those workers
    and flags it; the user can also set a custom label via the param.
  - Build surface (v6.5): `/worker` command (argument-hint + arg
    passing), worker-instructions DECLARE step (label rule), plane
    instructions (name-by-label rule), board claim-line rendering.
    Small slice.
- Open: confirm default-short + optional-param shape (see §5).

### 4.5 Board at scale — views vs DB (discussion 2026-11-24 — NOT decided)

- User's thought: as the number of tasks grows, the board holds too
  much information — are we back to the DB talk?
- Measurement (assistant, synthetic 100-task fixture on the v6.4 tree):
  `board.sh` full generation takes **16.5 s at 100 tasks** (overview
  298 KB, 100 task pages) — O(tasks) with a large bash constant
  (per-task page generation spawns many greps/awks). At the live 19
  tasks the overview was 78 KB; linearly that is ~3 s per generation.
- Separation of three problems (assistant's read, not decided):
  - **Density** (too much on the page) is a UI problem: default-hide
    DONE/DELIVERED behind an archive view, keep the gates inbox as
    the primary surface. No DB needed.
  - **Generation cost** (16.5 s) is an implementation problem:
    incremental regen (only the changed task's page + overview) or a
    faster generator. No DB needed — the data is small; the cost is
    process churn, and a DB would not remove the 100 page renders.
  - **Storage/query** is what a DB would actually fix: cross-task
    queries without scanning, concurrent writes, multi-machine shared
    state (the original 2026-11-12 parked reason). None of those is
    the board-density problem.
- So the DB talk is worth reopening only if the goal is again
  multi-machine collaboration, or if measurements prove file scanning
  itself is the bottleneck (it isn't so far — generation is). The
  board-scale problem is a board problem: views + incremental regen.
- **User decision 2026-11-24: too early to think about
  organization-level now.** The DB / multi-machine / org-scale
  question is deferred, not rejected. Board scale stays a
  project-level concern (views, and incremental regen if the measured
  generation cost ever bites at real task counts).
- Open: anticipated task count, and what "too much" feels like (page
  length, finding one task, or slowness) — see §5.
